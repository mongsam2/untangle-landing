# Git 규약

브랜치를 만들 때, GitHub 이슈를 작성·수정할 때, 커밋할 때, PR을 올릴 때 읽는다.

## 0. 목차

1. [Git Branch](#1-git-branch) — 브랜치 구분, 이름, 분기 기준과 PR 대상
2. [GitHub Issue](#2-github-issue) — 본문 구성과 문체, 관련 스펙 연결
3. [Git Commit](#3-git-commit) — 접두어와 메시지 작성
4. [GitHub PR](#4-github-pr) — 제목·본문 구성과 문체

## 1. Git Branch

### 1.1 구분

| 구분       | 사용                           | 예                            |
| ---------- | ------------------------------ | ----------------------------- |
| `feature`  | 기능 추가·변경                 | `feature/chat-rate-limit`     |
| `bugfix`   | 버그 수정                      | `bugfix/demo-resume-state`    |
| `hotfix`   | 바로 반영해야 하는 긴급 수정   | `hotfix/security-patch`       |
| `refactor` | 동작 변화 없는 코드 구조 개선  | `refactor/extract-chat-proxy` |
| `release`  | 릴리스 준비                    | `release/v1.2.0`              |
| `chore`    | 의존성·설정·빌드·문서 등 그 외 | `chore/update-dependencies`   |

- 브랜치 구분은 3번의 커밋 접두어와 별개 체계다.
  같은 값을 쓰려고 맞추지 않는다.
  예를 들어 지침 문서만 고치는 `chore/update-guidelines` 브랜치의 커밋 제목은
  `docs: ...`가 된다.

### 1.2 이름

- `<구분>/<짧은-설명>` 형식이며 영어 소문자와 하이픈으로 작성한다.
- GitHub 이슈가 있는 작업은 `<구분>/<이슈-번호>-<짧은-설명>` 형식을 쓴다.
  번호는 GitHub가 발급한 값만 사용하며 저장소 문서를 보고 직접 배정하지 않는다.
- `release`만 `release/<버전>` 형식을 쓴다.

### 1.3 분기 기준

- 사용자가 따로 명시하지 않았다면 브랜치는 최신 `main`에서 분기한다.

### 1.4 PR 대상 브랜치

- 작업 브랜치의 PR은 `main`을 대상으로 보낸다.

## 2. GitHub Issue

- `gh` CLI를 사용하여 작업한다.

### 2.1 본문 구성

`.github/ISSUE_TEMPLATE/feature.md`의 섹션과 순서를 그대로 사용한다.

| 섹션             | 내용                                         |
| ---------------- | -------------------------------------------- |
| `의존 관계`      | 선행·후속 이슈 번호. 없으면 `없음`           |
| `목적`           | 작업으로 달성할 결과와 필요한 이유           |
| `배경`           | 현재 상태, 문제 상황과 관련 맥락             |
| `범위`           | 구현·변경할 내용과 이번 작업에서 제외할 내용 |
| `작업 계획`      | 주요 작업 단위를 수행 순서대로 정리          |
| `예상 변경 영역` | 디렉터리나 주요 파일과 해당 위치의 예상 작업 |
| `관련 스펙 문서` | 연결된 스펙 문서 경로. 없으면 `없음`         |
| `참고`           | 관련 문서, 로그, 화면과 기존 PR              |

- `목적`과 `배경`을 포함한 설명은 목록으로 작성한다.
- 제외 범위는 `### 제외` 밑에 리스트로 작성한다.
- `예상 변경 영역`은 `<경로>: <예상 작업>` 형식으로 작성한다.
- 상세 계약과 구현 결정에 스펙이 필요하면 독립적으로 작성한 스펙 문서를 이슈에서
  연결한다.

### 2.2 문체

- 본문은 개조식으로 작성한다.
- `~다`로 끝나는 서술형 문장 대신 `구현`, `연결`, `검증`, `제외`, `필요`처럼
  짧은 명사형이나 동사형 표현을 사용한다.
- 작업한 사람만 아는 맥락과 모호한 약어를 피하고 처음 읽는 팀원이 이해할 수 있게 쓴다.
- 한 줄이 길어지면 100자 안팎에서 끊는다.

### 2.3 관련 스펙 문서

스펙 문서의 생성 기준, 작성 형식과 유지 관리는
[문서 작성 및 유지 관리 규약](documentation.md)을 따른다.

스펙 문서는 GitHub 이슈와 독립적으로 작성하며 이슈를 역으로 연결하지 않는다.
작업에 참고할 스펙이 있으면 GitHub 이슈의 `관련 스펙 문서`에 현재 경로를 적고,
없으면 `없음`으로 둔다.

## 3. Git Commit

### 3.1 제목

- `접두어: <메시지>` 형식
- 접두어는 아래 표를 참고하고, 메시지는 한국어로 작성

| 접두어     | 사용                                                                                                                                             |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `feat`     | 기능 추가·변경                                                                                                                                   |
| `fix`      | 버그 수정                                                                                                                                        |
| `docs`     | `docs/`와 Markdown 지침·안내 문서 변경                                                                                                           |
| `refactor` | 동작 변화 없는 코드 구조 개선                                                                                                                    |
| `chore`    | 의존성·설정·빌드 등 (`package.json`, `bun.lock`, `next.config.ts`, `eslint.config.mjs`, `tsconfig.json`, `.prettierrc`, `.env.example`, CI 설정) |

### 3.2 본문

- 제목은 요약형으로 한 줄. 바뀐 코드 중에 가장 중요하다고 생각하는 변경 사항이 드러나게 적는다.
- 본문은 전부 한국어로 쓰고, 제목과 한 줄 띄운다.
- 본문 첫 문단에 이 변경이 왜 필요했는지를 한두 문장으로 적는다.
  제목만으로 이유가 분명하면 생략한다.
- 그 아래 한 줄 띄우고, 무엇을 했는지 `-` 목록으로 적는다.
  세부 내용이 필요하면 들여써서 하위 항목으로 적는다.
- 목록 항목은 코드를 열지 않아도 이해되는 단위로 쓴다.
  **바뀐 파일 목록은 적지 않는다.** `git show`가 이미 보여준다.
- 한 줄이 길어지면 40~50자 안팎에서 끊는다.

### 3.3 예시

**`feat` — 기능 추가**

```
feat: 소감 폼에 사용자 인터뷰 참여 의향 항목 추가

체험을 마친 사람 중에서 인터뷰에 응할 사람을 가려낼 방법이 없었다.

- 인터뷰 참여 의향을 묻는 항목을 폼에 추가한다
- 의향을 체크하면 연락처를 필수 항목으로 바꾼다
- 서버 함수에서 연락처 형식을 다시 검증한다
```

**`fix` — 버그 수정**

```
fix: 데모에 다시 들어오면 이전 진행 상태가 사라지는 문제 수정

저장된 상태를 읽기 전에 초기값으로 덮어써서, 새로고침하면
처음 화면으로 되돌아가는 문제가 있었다.

- 저장된 상태를 먼저 읽고 나서 초기값을 정한다
- 저장 형식이 바뀐 경우에는 이어하기를 제안하지 않는다
```

**`docs` — 문서 변경** (제목에서 이유가 분명해 첫 문단을 생략한 예)

```
docs: README에 로컬 개발 환경 구성 방법 추가

- `bun install`로 의존성을 설치하고 개발 서버를 실행하는 순서를 정리한다
- 필요한 환경 변수와 예시 값을 함께 적는다
```

**`refactor` — 구조 개선**

```
refactor: Route Handler의 외부 호출 코드를 lib으로 분리

Route Handler가 외부 서버를 직접 호출해 검증과 전송 책임이 섞여 있었다.

- 주소 정규화와 전송을 `lib/chat/proxy.ts`로 옮긴다
- Route Handler는 본문을 읽고 검증한 뒤 그 함수를 부르게 한다
```

**`chore` — 의존성·설정·빌드** (항목별 이유를 하위 항목으로 붙인 예)

```
chore: 포매터 도입 및 검증 스크립트 정리

- Prettier를 추가하고 ESLint의 포매팅 규칙을 끈다
  - 두 도구가 같은 줄을 서로 다르게 고쳐 충돌이 났다
- `format`과 `typecheck` 스크립트를 추가한다
```

## 4. GitHub PR

- `gh` CLI를 사용하여 작업.
- PR을 보낼 대상 브랜치는 [1.4](#14-pr-대상-브랜치)을 따른다.

### 4.1 제목

- [`브랜치 접두어`] `한 줄 설명`
- `브랜치 접두어`: 작업 브랜치의 구분을 그대로 사용 ([1.1](#11-구분))
- `한 줄 설명`: 수행한 일을 간단하게 한 줄로 서술

### 4.2 본문 구성

`.github/PULL_REQUEST_TEMPLATE.md`의 네 섹션을 그대로 사용한다.
웹에서 PR을 만들면 이 템플릿이 자동으로 채워지고, `gh`로 만들 때는 같은 구성을 직접 맞춘다.

- 이번 PR이 닫는 이슈만 적는다. 상위 이슈와 후속 이슈는 적지 않는다.
- **변경된 모든 내용을 적는 게 목표가 아니다.** 리뷰어가 알아야 할 것만 남긴다.
- 이번 PR에서 제외한 내용은 `구현 방식과 주요 결정` 아래에 `### 범위에서 제외`라는
  하위 제목을 두고 목록으로 작성한다. 범위에서 제외는 PR을 읽는 사람이 작업의 범위를 더 넓게
  생각할 여지가 있는 경우에만 작성한다. (분량이 크면 안 된다.)
- 엔드포인트를 추가하거나 요청·응답 형식을 바꿨으면 `변경 사항 요약` 아래에
  `### 요청·응답 예시` 하위 제목을 두고 대표 요청과 응답을 코드 블록으로 붙인다.
  경로마다 대표 사례 하나씩만 두고 모든 필드 조합을 나열하지 않는다.
  값은 그대로 보내도 정상 응답을 받는 값을 쓴다.
- 화면이 눈에 띄게 달라졌으면 `변경 사항 요약` 아래에 `### 화면 변화` 하위 제목을 두고
  대표 화면을 하나씩 붙인다. 화면마다 하나씩만 두고 모든 상태를 나열하지 않는다.
  바뀐 부분을 비교해서 봐야 하면 변경 전과 후를 함께 붙인다.
- 해당 사항이 없는 섹션은 지운다.

### 4.3 문체

- 개조식으로 쓰고 `~다`로 끝나는 서술형 문장을 쓰지 않는다.
  짧은 명사형이나 동사로 끝낸다: `~통일`, `~변환`, `~준비`, `~제외`, `~없음`, `~필요`.
- 작업한 사람만 아는 맥락과 내부 구현 세부는 뺀다. 처음 읽는 팀원이 이해할 수 있게 쓴다.
- `파괴적 변경`처럼 단정적인 평가 대신 무엇이 어떻게 바뀌는지 사실만 적는다.
- 한 줄이 길어지면 100자 안팎에서 끊는다.
