## 1. 구현 원칙

### 기준 문서

- `intent.md`는 제품 목적과 사용자 경험을 판단하는 기준이다.
- `spec.md`는 브라우저 상태, 화면 행동, 프록시와 오류 계약을 판단하는 기준이다.
- 이 문서는 구현 순서와 단계별 검증만 결정하며 상위 문서의 의미를 넓히지 않는다.
- 구현 중 계약 변경이 필요하면 코드를 먼저 바꾸지 않고 `spec.md`를 `In Review`로
  되돌려 변경 이유와 영향을 기록한 뒤 다시 승인받는다.

### 작게 나누어 단계별로 구현

- 공개 타입과 검증, 프록시, 브라우저 상태, 채팅 UI, 오늘 UI를 순서대로 구현한다.
- 먼저 네트워크와 화면에 의존하지 않는 계약과 상태 로직을 테스트로 고정한다.
- AI 서버를 대신하는 테스트용 응답으로 `/api/chat`의 성공·오류 처리를 완성한 뒤 화면을
  연결한다.
- 각 단계의 검증과 완료 조건을 통과한 뒤에만 다음 단계로 넘어간다.

### 데이터가 들어오고 나갈 때 엄격히 검증

- 브라우저 입력, AI 서버 성공·오류 응답과 localStorage 복원 값을 각각 검증한다.
- UI 전용 메시지 필드와 완료 상태를 AI 요청에서 구조적으로 제거한다.
- 네트워크 예외와 AI 서버가 보낸 원문은 사용자 응답과 로그에 노출하지 않는다.
- ID를 비교해 완료 상태를 맞추는 일은 모델이나 화면 컴포넌트가 아니라 순수 함수가
  담당한다.

## 2. 기술 기준

| 영역          | 선택                                                            |
| ------------- | --------------------------------------------------------------- |
| 프레임워크    | Next.js 16.2.10 App Router, React 19.2.4                        |
| 언어          | TypeScript strict mode                                          |
| 스타일        | 기존 Tailwind CSS 4와 전역 Untangle 토큰                        |
| 패키지·실행   | Bun과 `bun.lock`                                                |
| 단위 테스트   | Bun 내장 test runner                                            |
| 서버 호출     | Node.js Route Handler와 표준 `fetch`                            |
| 브라우저 저장 | `localStorage`, Web Crypto UUIDv4                               |
| 재정렬        | `@dnd-kit/react`, `@dnd-kit/helpers`와 메뉴를 통한 위·아래 이동 |

- Route Handler, 서버·클라이언트 코드 구분과 환경 변수는 저장소에 설치된 Next.js 문서를 먼저
  읽고 현재 버전의 규약을 따른다.
- `UNTANGLE_AI_BASE_URL`은 `NEXT_PUBLIC_` 접두사 없이 서버에서만 읽는다.
- 클라이언트 상태에는 React의 `useReducer`를 사용하고 별도 전역 상태 라이브러리를
  추가하지 않는다.
- 직접 공급자 SDK와 분석 SDK는 남기지 않는다.
- 재정렬 라이브러리는 Pointer Events 기반 터치·마우스 입력과 키보드 센서를 지원하는
  현재 React API만 사용하고 이전 버전 패키지는 추가하지 않는다.

- `app/`은 라우트 진입점만 두고 검증과 AI 서버 호출은 `lib/chat/`에 둔다.
- `lib/chat/types.ts`는 브라우저와 서버가 공유하는 공개 데이터 타입만 가진다.
- `lib/chat/contract.ts`는 허용한 필드만 받는 런타임 검증, 값 정리와 오류 분류를 담당하며
  React와 Next.js에 의존하지 않는다.
- `lib/chat/proxy.ts`는 서버 전용 환경 변수와 AI 서버 호출을 담당하고 클라이언트
  모듈에서 import할 수 없게 표시한다.
- `components/demo/types.ts`는 저장 메시지, 완료 상태와 편집 UI처럼 데모 전용 타입만
  정의한다.
- `components/demo/state.ts`는 reducer, 저장 검증, 대화 정리와 완료 상태를 새 목록에
  맞추는 순수 함수를 제공한다.
- 실제 구현 중 한 파일이 너무 커지면 같은 이름의 디렉터리로 나누되 `app → components →
lib` 의존 방향은 바꾸지 않는다.

## 4. 요청과 상태 처리 흐름

```text
localStorage v2 검증·복원 또는 새 첫 인사 생성
  → 사용자 메시지 추가
  → 오래된 사용자·assistant 대화 쌍을 지워 63개·256 KiB 안으로 정리
  → UI 필드를 제거한 ChatRequest 생성
  → POST /api/chat
  → 실제 본문 크기와 공개 요청 검증
  → 기본 공급자를 사용하는 AI 서버 /v1/chat 호출
  → 성공 또는 오류 구조와 request ID 검증
  → 브라우저 응답 반환
  → chat: assistant 메시지만 추가
     tasks: assistant+요약 추가, 전체 목록 교체, 새 목록에 완료 상태 맞춤, 오늘 알림 표시
  → 검증된 v2 상태 저장
```

직접 편집은 현재 `tasks`와 완료 ID를 하나의 reducer action으로 함께 바꾼다. AI 요청 중에는 내용
편집을 잠그고 완료 체크만 별도 상태로 허용한다. 응답을 반영할 때는 요청 시작 시점의
목록과 응답을 기준으로 목록 내용을 통째로 교체하고, 응답 시점의 최신 완료 ID를 새
목록의 ID에 맞춘다.

## 5. 작업 단계

### 구현 전 확인. SDLC 문서 승인

작업:

- `intent.md`와 `spec.md`의 승인 상태와 승인자를 확인한다.
- 이 `plan.md`에 목표 파일, 순서, 단계별 검사와 완료 조건을 기록한다.
- 현재 작업 트리의 변경 파일을 확인하고 기존 변경을 보존할 방법을 정한다.

검증:

- 구현자가 다른 저장소의 설계 문서를 읽지 않아도 `spec.md`만으로 계약을 구현할 수 있다.
- 각 승인 요구사항이 아래 단계와 검증 항목 중 하나 이상에 연결되어 있다.
- 구현 전에 필요한 제품 선택이 남아 있지 않다.

완료 조건:

- 제품 책임자가 이 문서를 승인하고 `상태`, `승인일`, `승인자`가 기록되어 있다.

진행 조건: 이 조건을 만족하기 전에는 애플리케이션 코드를 수정하지 않는다.

### 단계 1. 공개 타입, 런타임 검증과 기본 테스트

작업:

- 설치된 Next.js 16.2.10의 Route Handler, Server/Client Component와 환경 변수 문서를
  읽고 사용할 API를 확인한다.
- `lib/chat/types.ts`에 Message, Task, Subtask, 성공·오류와 요청 타입을 정의한다.
- `lib/chat/contract.ts`에 알 수 없는 필드를 거절하는 객체 검증, 문자열 공백·길이,
  UUID, 중복 ID, 배열 최대 개수, 응답 종류와 HTTP 상태·오류 코드 검증을 순수 함수로
  구현한다.
- 실제 UTF-8 JSON 바이트 계산과 전송용 메시지 변환 함수를 구현한다.
- Bun test script와 테스트 디렉터리를 구성한다.

검증:

- 모든 필드의 최소값, 최대값과 최대값을 하나 넘은 값을 테스트한다.
- 알 수 없는 필드, 역할, 마지막 메시지, UUID 대소문자 중복과 부모·자식 중복을
  테스트한다.
- `chat`과 `tasks` 필드 혼합, 잘못된 오류 상태·코드 조합을 거절한다.
- UI 전용 필드가 전송 요청에 들어가지 않는지 검사한다.
- `bun run test`와 기존 lint·typecheck가 통과한다.

완료 조건:

- 네트워크와 React 없이 공개 계약의 모든 규칙을 테스트할 수 있다.
- 다음 단계가 같은 검증 함수를 프록시와 브라우저에서 공유할 수 있다.

### 단계 2. Next.js AI 프록시 전체 요청 흐름

작업:

- `.env.example`에 서버 전용 `UNTANGLE_AI_BASE_URL`과 로컬 기본값을 설명한다.
- `lib/chat/proxy.ts`에 URL 정리, 65초 제한, 캐시하지 않는 요청, 성공·오류 및 request ID
  선택 규칙을 구현한다.
- `app/api/chat/route.ts`에서 실제 본문 크기를 JSON 파싱 전에 검사하고 공개 요청을
  검증한 뒤 proxy 함수를 호출한다.
- 프록시가 만드는 모든 응답에 `X-Request-ID`를 붙이고 안전한 오류 본문을 사용한다.
- fetch를 가짜 함수로 주입해 네트워크 없이 전체 경로를 테스트한다.

검증:

- 유효한 `chat`과 `tasks` 응답이 200으로 전달된다.
- 브라우저가 `provider`를 보내거나 요청 계약을 어기면 AI 서버를 호출하지 않는다.
- 256 KiB 초과, JSON 오류, 422 검증 오류가 명세 상태와 코드로 구분된다.
- AI 서버 오류, 연결 실패, timeout, 잘못된 JSON·스키마·request ID를 모두 테스트한다.
- 요청·응답·예외 원문을 로그나 공개 오류에 넣지 않는지 고유 표식으로 검사한다.

완료 조건:

- 실제 공급자 키 없이 `/api/chat`의 모든 성공·실패 처리를 같은 결과로 반복 검증할 수 있다.
- Route Handler에는 본문 읽기, 검증 함수 호출과 응답 반환 외의 업무 규칙이 남지 않는다.

### 단계 3. 데모 상태, 저장과 완료 상태 맞추기

작업:

- `components/demo/types.ts`에 StoredMessage, TaskSummary, StoredDemoState와 reducer action을
  정의한다.
- 새 상태, 사용자·assistant 메시지, 재시도, 탭 읽음 표시와 전체 목록 교체 reducer를
  구현한다.
- 메시지 64개와 요청 256 KiB 제한을 지키도록 오래된 사용자·assistant 대화 쌍을 지우고
  `historyTrimmed` 안내를 구현한다.
- v2 저장 데이터에서 알 수 없는 필드를 거절하는 검증, 초기 복원과 저장 실패 시 동작을
  구현한다.
- ID 기반 완료 상태, 부모·자식 연동과 새 목록에 완료 상태를 맞추는 로직을 구현한다.
- 직접 추가·수정·삭제·재정렬을 순수 상태 전환으로 구현한다.

검증:

- v1 무시, 정상 v2 복원, 손상된 v2 전체 폐기와 복원 전 덮어쓰기 방지를 테스트한다.
- 실패 후 같은 사용자 메시지를 중복하지 않는 재시도와 재방문 재시도를 테스트한다.
- 오래된 대화 정리 순서, 안내 표시와 최신 사용자 메시지 보존을 테스트한다.
- `chat` 응답이 목록을 바꾸지 않는지, `tasks` 응답이 전체 목록을 교체하고 당시 요약을
  보존하는지 테스트한다.
- 제목·위치 변경 시 완료 보존, 삭제·신규 항목과 서브태스크 유무 전환을 테스트한다.
- 직접 추가·조회·수정·삭제, 부모 체크, 완료 그룹 이동과 최대 7개 제한을 테스트한다.

완료 조건:

- 화면 없이 모든 상태 변경과 저장 결과를 같은 조건에서 반복 검증할 수 있다.
- 어떤 변경 뒤에도 중복 ID, 삭제된 할 일의 완료 ID나 계약에 없는 데이터가 남지 않는다.

### 단계 4. 연속 채팅 화면과 공통 탭 레이아웃

작업:

- `/demo`의 서버 컴포넌트 화면 구조와 metadata를 새 대화 경험에 맞게 갱신한다.
- `DemoFlow` 한 곳에서 v2 클라이언트 상태를 관리하도록 교체한다.
- 기존 헤더, 로고, 데모 배지와 닫기 동선을 유지한다.
- `대화`/`오늘` 하단 탭, 새 할 일 알림 점과 빈 오늘 화면을 연결한다.
- 첫 인사, 말풍선, 자동 스크롤, 4,000자 입력, 한글 조합 중 오작동하지 않는 전송과 대기
  표시를 구현한다.
- `/api/chat` 호출, 오류 표시와 사용자 메시지 비중복 재시도를 연결한다.
- `tasks` 응답에 응답 당시의 할 일 요약 카드와 `오늘에서 보기`를 표시한다.

검증:

- 새 방문, 정상 대화, 재방문과 응답 전 종료 복원을 브라우저에서 확인한다.
- `chat` 응답은 목록과 오늘 알림을 바꾸지 않고 `tasks` 응답만 오늘 알림을 켠다.
- 메시지 전송 후 자동 탭 전환이 없고 두 이동 수단이 같은 오늘 화면을 연다.
- 요청 중 중복 전송이 되지 않고 실패 뒤 입력·대화·목록이 보존된다.
- 모바일 키보드가 입력과 하단 탭을 가리지 않는지 확인한다.

완료 조건:

- 테스트용 또는 로컬 AI 응답으로 첫 대화부터 목록 요약까지 전체 흐름이 동작한다.
- 기존 단계 상태에 의존하지 않는 새 채팅 경험이 완성된다.

### 단계 5. 오늘 할 일 실행과 직접 편집

작업:

- 현재 dnd-kit React 패키지와 sortable helper를 추가하고 lockfile을 갱신한다.

## 11. 승인 요청

제품 책임자는 다음을 확인한다.

- 계약 → 프록시 → 상태 → 채팅 → 오늘 → 제거 → 최종 검증 순서가 적절한가
- 각 단계가 다음 단계 전에 오류 범위를 충분히 줄이는가
- 현재 작업 트리 보존 방법과 계약 변경 전 승인 조건이 충분한가
- 실제 공급자 연동이 없으면 완료하지 않는 조건이 적절한가
- 로컬 검증과 REVIEW 작성에서 이번 라이프사이클을 종료하는가

승인 후 `상태`, `승인일`, `승인자`를 갱신하고 단계 1부터 구현한다.
