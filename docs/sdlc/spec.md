## 1. 목적

이 문서는 승인된 제품 의도를 Next.js 데모로 구현하기 위한 화면 행동, 브라우저 상태,
서버 프록시와 검증 계약으로 구체화한다. 구현자가 다른 저장소의 문서를 참조하지 않아도
필요한 타입, 제한, 상태 전환과 오류 처리를 구현할 수 있도록 랜딩이 사용하는 AI 공개
경계를 이 문서 안에 완전하게 정의한다.

## 2. 범위

### 포함

- 연속 채팅과 분리된 `오늘` 화면을 가진 `/demo`
- `untangle-ai`로만 AI 요청을 보내는 Next.js Route Handler
- 대화, 할 일과 완료 상태의 브라우저 저장 및 자동 복원
- AI 전체 목록 응답과 로컬 완료 상태의 ID 기반 조정
- 큰 할 일과 서브태스크의 직접 생성·수정·삭제·재정렬
- `/register`로 가는 비간섭형 소감 링크
- 기존 단계형 데모, 직접 공급자 호출과 미사용 코드 제거
- PostHog 코드·의존성·설정·문서와 개인정보 안내 제거
- 실제 동작에 맞는 개인정보 처리방침 수정

### 제외

- 랜딩 홈의 문구와 섹션 구성 변경
- AI 서버의 API, 프롬프트, 모델과 공급자 선택 변경
- 사용자 계정, 서버 저장, 동기화와 날짜별 기록
- 완료 상태의 AI 전달
- 데모 전체 초기화 UI
- PostHog에 이미 전송된 과거 원격 데이터의 관리
- 배포와 운영 환경 변경

## 3. 시스템 경계

```text
브라우저
  ├─ localStorage: 대화, 최신 할 일, 완료 ID
  └─ POST /api/chat
         ↓
untangle-landing Next.js 서버
  └─ POST {UNTANGLE_AI_BASE_URL}/v1/chat
         ↓
untangle-ai → 기본 GPT 또는 Claude 공급자
```

- 브라우저는 AI 서버 주소와 공급자 설정을 알지 못한다.
- Next.js 서버는 요청을 검증하고 전달할 뿐 대화와 목록을 저장하지 않는다.
- 브라우저 요청에는 `provider`를 허용하지 않으며 AI 서버의 기본 공급자를 사용한다.
- AI 서버의 `tasks`는 할 일 내용의 원본이고, 브라우저의 완료 ID는 표시 상태의 원본이다.
- 직접 편집 후에는 브라우저 목록이 최신 원본이 되며 다음 AI 요청에 전체 목록으로
  전달된다.

### 3.1 공통 값과 검증 규칙

- 모든 객체는 아래에 명시한 필드만 허용하며 중첩 객체에도 같은 규칙을 적용한다.
- 모든 문자열은 앞뒤 공백을 제거한 뒤 길이를 검사하고 저장·전달한다.
- UUID는 하이픈을 포함한 `8-4-4-4-12` 16진수 표기만 허용한다. 영문 16진수는 대소문자
  모두 허용하지만 대소문자만 다른 같은 UUID는 중복으로 본다.
- 하나의 `tasks` 배열 안에서는 큰 할 일과 모든 서브태스크의 ID가 서로 달라야 한다.
- 브라우저에서 직접 만드는 새 ID와 로컬 메시지 ID는 UUIDv4다.
- 알 수 없는 필드, 잘못된 타입, 빈 필수 문자열과 제한 초과 값은 자동으로 고치거나
  버리지 않고 검증 실패로 처리한다.

### 3.2 대화와 할 일 타입

`Message`:

```json
{
  "role": "user",
  "content": "요즘 논문 때문에 정신이 없어"
}
```

| 필드      | 형식                    | 제한                   |
| --------- | ----------------------- | ---------------------- |
| `role`    | `"user" \| "assistant"` | 필수                   |
| `content` | 문자열                  | 공백 제거 후 1~4,000자 |

`Subtask`:

```json
{
  "id": "d913da20-bfae-46dd-9cc7-0e15de399d45",
  "title": "논문 파일 열기"
}
```

| 필드    | 형식        | 제한                 |
| ------- | ----------- | -------------------- |
| `id`    | UUID 문자열 | 필수                 |
| `title` | 문자열      | 공백 제거 후 1~100자 |

`Task`:

```json
{
  "id": "0da6c6a5-6cc3-448c-857a-1917fc3af3d8",
  "title": "논문 초안 작성하기",
  "description": "모아둔 자료를 바탕으로 논문의 첫 초안을 만들어요.",
  "subtasks": [
    {
      "id": "d913da20-bfae-46dd-9cc7-0e15de399d45",
      "title": "논문 파일 열기"
    }
  ]
}
```

| 필드          | 형식        | 제한                 |
| ------------- | ----------- | -------------------- |
| `id`          | UUID 문자열 | 필수                 |
| `title`       | 문자열      | 공백 제거 후 1~100자 |
| `description` | 문자열      | 공백 제거 후 1~500자 |
| `subtasks`    | `Subtask[]` | 필수, 0~7개          |

### 3.3 채팅 요청

브라우저와 Next.js 프록시가 사용하는 요청은 `ChatRequest`다.

```json
{
  "messages": [
    {
      "role": "assistant",
      "content": "안녕하세요. 요즘 머릿속을 복잡하게 만드는 일이 있나요?"
    },
    {
      "role": "user",
      "content": "논문이랑 밀린 빨래가 계속 신경 쓰여"
    }
  ],
  "tasks": []
}
```

| 필드       | 형식        | 제한                               |
| ---------- | ----------- | ---------------------------------- |
| `messages` | `Message[]` | 필수, 1~64개, 마지막 항목은 `user` |
| `tasks`    | `Task[]`    | 필수, 0~7개                        |

- HTTP 요청 본문은 UTF-8로 직렬화한 실제 수신 바이트 기준 최대 256 KiB다.
- `system`과 `developer` 역할은 허용하지 않는다.
- assistant 메시지의 `content`에는 직전 AI 응답의 `message`만 넣는다.
- 채팅 요약 카드, 로컬 메시지 ID, 완료 상태와 다른 UI 필드는 요청에 넣지 않는다.
- `provider` 필드는 브라우저 요청과 AI 서버 전달 요청 모두에 넣지 않는다. AI 서버가
  설정된 기본 공급자를 선택한다.
- Next.js 프록시는 검증을 통과한 `messages`와 `tasks`만 같은 JSON 구조로 AI 서버에
  전달한다.

### 3.4 성공 응답

`ChatResponse`는 목록이 바뀌지 않은 응답이다.

```json
{
  "type": "chat",
  "message": "논문은 지금 어느 정도까지 진행됐어요?"
}
```

- `type`은 `chat`만 허용한다.
- `message`는 공백 제거 후 1~500자다.
- `tasks` 필드를 허용하지 않으며 브라우저의 현재 목록을 그대로 유지한다.

`TasksResponse`는 목록이 바뀐 응답이다.

```json
{
  "type": "tasks",
  "message": "지금 할 일을 정리해봤어요. 이 중 막막하게 느껴지는 일이 있나요?",
  "tasks": [
    {
      "id": "0da6c6a5-6cc3-448c-857a-1917fc3af3d8",
      "title": "논문 초안 작성하기",
      "description": "모아둔 자료를 바탕으로 논문의 첫 초안을 만들어요.",
      "subtasks": []
    }
  ]
}
```

- `type`은 `tasks`만 허용한다.
- `message`는 공백 제거 후 1~500자다.
- `tasks`는 변경 후의 최신 전체 목록이며 `Task[]`의 모든 제한을 만족해야 한다.
- 목록 생성과 일부 변경은 1~7개의 큰 할 일을 반환한다.
- 사용자가 전체 삭제를 명시적으로 요청한 응답만 빈 배열을 반환할 수 있다. 프록시는
  AI 서버가 사용자 의도를 판정한 결과를 신뢰하므로 구조가 유효한 빈 배열을 허용한다.
- 성공 응답은 `type`으로 판별하며 두 형태의 필드를 섞을 수 없다.
- 두 성공 응답의 HTTP 상태는 200이고 `application/json`으로 반환한다.
- 응답은 스트리밍하지 않고 완성된 JSON 한 건으로 반환한다.

### 3.5 오류 응답

AI 서버와 Next.js 프록시의 모든 오류는 `ErrorResponse`로 브라우저에 반환한다.

```json
{
  "error": {
    "code": "provider_timeout",
    "message": "AI 응답이 늦어지고 있어요. 잠시 후 다시 시도해 주세요.",
    "request_id": "b777dd74-f22e-4bbc-aac6-3a6a14a0459b"
  }
}
```

| 필드               | 형식             | 제한                                              |
| ------------------ | ---------------- | ------------------------------------------------- |
| `error.code`       | 아래 표의 문자열 | 필수                                              |
| `error.message`    | 문자열           | 공백 제거 후 1~200자, 사용자에게 표시 가능해야 함 |
| `error.request_id` | UUID 문자열      | 필수                                              |

AI 서버에서 전달되는 오류:

| HTTP | `code`                    | 의미                                              |
| ---- | ------------------------- | ------------------------------------------------- |
| 400  | `invalid_request`         | JSON 파싱 실패 또는 마지막 메시지가 `user`가 아님 |
| 413  | `request_too_large`       | 실제 본문이 256 KiB 초과                          |
| 422  | `validation_error`        | 필드, 타입, 길이, 개수, UUID 또는 중복 ID 오류    |
| 429  | `provider_rate_limited`   | 기본 공급자의 사용량 제한                         |
| 502  | `provider_error`          | 공급자 오류 또는 비정상 종료                      |
| 502  | `model_output_invalid`    | 공급자 출력의 구조 또는 목록 참조가 유효하지 않음 |
| 503  | `provider_not_configured` | 기본 공급자, 모델 또는 키 설정 누락               |
| 504  | `provider_timeout`        | AI 서버의 공급자 호출 제한 시간 초과              |
| 500  | `internal_error`          | 분류되지 않은 AI 서버 오류                        |

Next.js 프록시가 직접 만드는 오류:

| HTTP | `code`                | 고정 `message`                                             |
| ---- | --------------------- | ---------------------------------------------------------- |
| 400  | `invalid_request`     | `요청 형식이 올바르지 않아요.`                             |
| 413  | `request_too_large`   | `한 번에 보낼 내용이 너무 많아요. 입력을 줄여 주세요.`     |
| 422  | `validation_error`    | `요청 내용을 확인해 주세요.`                               |
| 502  | `ai_unavailable`      | `AI 서버에 연결하지 못했어요. 잠시 후 다시 시도해 주세요.` |
| 502  | `ai_response_invalid` | `AI 응답을 확인하지 못했어요. 잠시 후 다시 시도해 주세요.` |
| 503  | `ai_not_configured`   | `AI 서버 연결이 준비되지 않았어요.`                        |
| 504  | `ai_timeout`          | `AI 응답이 늦어지고 있어요. 잠시 후 다시 시도해 주세요.`   |

- 프록시는 요청마다 UUIDv4 request ID를 먼저 만든다.
- AI 서버가 유효한 `X-Request-ID`를 반환하면 그 값을 브라우저 응답 헤더와 오류 본문에
  사용한다. 없거나 유효하지 않으면 프록시 request ID를 사용한다.
- 성공과 오류를 포함한 모든 `/api/chat` 응답에 `X-Request-ID` 헤더를 넣는다.
- 오류 본문의 `request_id`는 응답 헤더와 같아야 한다.
- AI 서버 오류 본문의 `request_id`와 유효한 `X-Request-ID`가 다르면 upstream 계약
  위반으로 보고 `ai_response_invalid`로 바꾼다. 헤더가 없을 때는 유효한 오류 본문의
  `request_id`를 사용하고, 둘 다 없거나 잘못되었으면 프록시 request ID를 넣은
  `ai_response_invalid`로 바꾼다.
- AI 서버가 위 표의 상태·코드 조합과 `ErrorResponse`를 정확히 반환했을 때만 오류를
  그대로 전달한다. 그 외 upstream 오류는 `ai_response_invalid`로 닫는다.
- 공급자 원문 오류, 프롬프트, 네트워크 예외 문자열, 메시지와 할 일은 오류 응답이나
  프록시 로그에 넣지 않는다.

## 4. 데모 화면 계약

### 4.1 공통 셸

- 기존 최대 480px 모바일 열, 보라색 디자인 토큰, 로고와 `데모` 배지를 유지한다.
- 헤더의 닫기 버튼은 저장 상태를 지우지 않고 랜딩 홈으로 이동한다.
- 콘텐츠 아래에 `대화`와 `오늘` 두 탭을 고정한다.
- 탭은 아이콘과 텍스트를 함께 사용하고 현재 탭을 색상 외의 표시로도 구분한다.
- 새 `tasks` 응답을 받은 뒤 사용자가 `오늘`을 열기 전까지 `오늘` 탭에 점 표시를 둔다.
- 탭 이동은 URL을 바꾸지 않는 `/demo` 내부 상태 전환이다.
- 재방문 시 저장 데이터는 복원하지만 첫 화면은 `대화` 탭으로 연다.

### 4.2 대화 화면

- 저장된 새 데모 상태가 없으면 첫 assistant 메시지로
  `안녕하세요. 요즘 머릿속을 복잡하게 만드는 일이 있나요?`를 보여준다.
- 첫 메시지도 대화 기록에 포함해 다음 요청 때 AI 서버로 전달한다.
- 사용자와 assistant 메시지를 시간순 말풍선으로 표시한다.
- 입력은 최대 4,000자이며 한국어 IME 조합 중 Enter로 전송하지 않는다.
- Enter는 전송, Shift+Enter는 줄바꿈이고 모바일에서는 전송 버튼을 제공한다.
- 요청 중에는 중복 전송을 막고 짧은 대기 표시를 보여준다.
- 사용자가 다른 탭으로 이동해도 요청과 대화 상태를 유지한다.
- 요청 실패 시 마지막 사용자 메시지를 남기고 인라인 오류와 `다시 시도`를 보여준다.
  재시도는 사용자 메시지를 중복 추가하지 않고 같은 최신 요청을 다시 보낸다.

### 4.3 AI 응답 표시

- `chat` 응답은 assistant 말풍선만 추가하고 현재 목록을 바꾸지 않는다.
- `tasks` 응답은 assistant 말풍선을 추가하고 현재 목록을 응답의 전체 스냅샷으로
  교체한다.
- `tasks` 말풍선 아래에는 현재 큰 할 일 개수와 제목을 최대 3개까지 보여주는 요약
  카드를 붙인다. 나머지가 있으면 남은 개수를 표시한다.
- 요약 카드는 과거 응답 시점의 제목과 개수를 보존한다. 이후 직접 편집으로 바뀌어도
  과거 카드 내용을 다시 쓰지 않는다.
- 요약 카드의 `오늘에서 보기`는 `오늘` 탭을 열고 새 목록 표시를 지운다.
- AI 응답을 받았다는 이유로 자동으로 탭을 바꾸지 않는다.

### 4.4 오늘 화면

- 상단에 현재 날짜와 `오늘의 할 일` 제목을 보여주되, 날짜가 바뀌어도 목록을 초기화하지
  않는다.
- 할 일이 없으면 빈 상태 설명과 `대화에서 정리하기` 버튼을 보여준다.
- 완료하지 않은 큰 할 일을 먼저, 완료한 큰 할 일을 그 아래에 표시한다.
- 각 그룹 안에서는 사용자가 정한 배열 순서를 유지한다.
- 큰 할 일 카드는 제목, 설명, 완료 컨트롤과 서브태스크를 보여준다.
- 큰 할 일과 서브태스크는 각각 최대 7개다.
- 화면 하단에 `/register?from=demo`로 가는 `체험 소감 남기기` 링크를 둔다.

## 5. 직접 목록 관리

### 5.1 생성과 수정

- 큰 할 일 추가와 수정은 제목과 설명을 필수로 받는다.
- 서브태스크 추가와 수정은 제목만 필수로 받는다.
- 앞뒤 공백을 제거하고 3.2의 제한을 적용한다.
  - 제목: 1~100자
  - 설명: 1~500자
- 새 항목은 브라우저의 `crypto.randomUUID()`로 UUIDv4를 발급한다. 이는 사용자가
  직접 만든 로컬 항목을 기존 백엔드 역할의 데모가 생성하는 경우다. AI가 만든 항목의
  ID는 계속 `untangle-ai`가 소유한다.
- AI 서버는 다음 요청에서 직접 만든 ID를 기존 항목 ID로 보존한다.
- 상한에 도달하면 추가 버튼을 비활성화하고 항목을 지운 뒤 추가하라는 안내를 표시한다.

### 5.2 삭제

- 큰 할 일 삭제 전에는 설명과 서브태스크도 함께 사라짐을 확인한다.
- 서브태스크 삭제도 항목 안에서 명시적인 확인을 거친다.
- 삭제한 ID의 완료 상태도 같은 상태 전환에서 제거한다.
- 마지막 큰 할 일을 직접 삭제하는 것을 허용한다.

### 5.3 재정렬

- 큰 할 일과 같은 부모의 서브태스크에 드래그 핸들을 제공한다.
- 재정렬은 같은 완료 그룹 또는 같은 부모 목록 안에서만 수행한다.
- 키보드와 스크린 리더 사용자는 더보기 메뉴의 `위로 이동`과 `아래로 이동`으로 같은
  결과를 만들 수 있어야 한다.
- 완료 상태 전환으로 항목이 그룹을 바꾸면 해당 그룹의 마지막 위치로 이동한다.
- 직접 재정렬은 새 대화 메시지를 만들지 않지만 다음 AI 요청의 배열 순서에 반영된다.

### 5.4 요청 중 편집

- AI 요청 중에도 `오늘` 화면 열기와 완료 체크는 허용한다.
- 추가, 내용 수정, 삭제와 재정렬은 응답이 올 때까지 비활성화한다. 요청에 사용한 목록과
  응답 시점 목록이 달라져 사용자 편집이 덮이는 경쟁 상태를 막기 위해서다.
- 요청이 끝나면 성공 여부와 관계없이 직접 편집을 다시 허용한다.

## 6. 완료 상태와 목록 조정

### 6.1 완료 상태 표현

- 저장 값은 완료된 항목 ID의 중복 없는 배열이다.
- 서브태스크가 없는 큰 할 일은 자신의 ID 포함 여부로 완료를 판단한다.
- 서브태스크가 있는 큰 할 일은 모든 현재 서브태스크 ID가 완료 배열에 있을 때 완료다.
- 서브태스크가 있는 큰 할 일의 부모 ID 자체는 완료 배열에 저장하지 않는다.
- 서브태스크가 있는 부모의 체크를 켜면 모든 자식 ID를 완료 배열에 넣고, 끄면 모두
  제거한다.
- 새 서브태스크가 완료된 부모에 추가되면 그 부모는 다시 미완료가 된다.

### 6.2 AI 전체 목록 응답 조정

1. 응답 전 각 기존 큰 할 일의 파생 완료 여부와 완료 ID를 기록한다.
2. 응답의 모든 큰 할 일과 서브태스크 ID 집합을 만든다.
3. 기존 완료 ID 중 새 집합에도 존재하는 ID만 유지한다.
4. 같은 ID의 제목, 설명이나 위치가 바뀌어도 완료 상태를 유지한다.
5. 서브태스크가 새로 생긴 부모의 자체 ID는 제거하고 새 자식은 미완료로 시작한다.
6. 서브태스크가 모두 사라져 leaf가 된 부모는 변경 전 부모가 완료였을 때만 부모 ID를
   완료로 넣는다.
7. 응답에서 사라진 항목의 완료 ID는 삭제하고 완전히 새로운 ID는 미완료로 시작한다.
8. 3.1~3.4로 응답 전체를 검증한 뒤에만 목록과 완료 상태를 함께 교체한다.

직접 편집에도 같은 원칙을 적용해 존재하지 않는 ID가 저장 데이터에 남지 않게 한다.

## 7. 브라우저 상태와 저장

### 7.1 저장 모델

새 키 `untangle:demo:v2`에 다음 `StoredDemoState`를 JSON으로 저장한다.

```text
StoredDemoState {
  version: 2
  messages: StoredMessage[]
  tasks: Task[]
  completedIds: UUID[]
  todayUnread: boolean
  historyTrimmed: boolean
}

StoredMessage {
  id: UUIDv4
  role: "user" | "assistant"
  content: 1~4,000자 문자열
  taskSummary?: {
    count: 0~7 정수
    titles: 0~3개의 1~100자 문자열
  }
}
```

- `taskSummary`는 `tasks` 응답으로 만든 assistant 메시지에만 허용한다.
- `taskSummary.count`는 해당 응답의 큰 할 일 수고, `titles`는 앞에서부터 최대 3개의
  제목을 복사한 값이다. `titles.length`는 `count`보다 클 수 없다.
- `messages`는 1~64개고 모든 메시지 ID는 서로 달라야 한다.
- `StoredMessage`를 AI 요청으로 바꿀 때는 `id`와 `taskSummary`를 제거하고 `role`과
  `content`만 사용한다.
- `tasks`는 3.2의 `Task[]`이며 0~7개다.
- `completedIds`는 현재 `tasks` 안에 존재하는 ID만 허용하고 중복을 허용하지 않는다.
- `historyTrimmed`는 길이 제한으로 과거 메시지를 제거한 적이 있는지를 나타낸다.

- 활성 탭, 입력 중 텍스트, 요청 중 상태, 오류와 열린 편집 UI는 저장하지 않는다.
- 기존 단계형 데모 키는 읽거나 변환하거나 삭제하지 않는다.
- 저장 데이터가 없거나 전체 검증에 실패하면 새 상태로 시작한다.
- 일부 필드만 추측해 복구하지 않는다. 손상된 목록을 AI에 보내는 것보다 안전한 새
  상태를 우선한다.
- `localStorage` 접근 실패는 데모 사용을 막지 않고 현재 탭의 메모리 상태로 계속한다.
- 초기 복원이 끝나기 전에 기본 상태를 저장해 기존 값을 덮지 않는다.
- 저장된 마지막 메시지가 `user`면 이전 요청이 응답 전에 끝난 것으로 보고, 복원 직후
  그 메시지를 중복 추가하지 않는 `응답 다시 받기` 상태를 보여준다.

### 7.2 장기 대화 상한

- 화면과 저장소에는 AI에 다시 보낼 수 있는 최근 메시지만 유지한다.
- 새 사용자 메시지를 추가한 뒤, 아직 보내지 않은 최신 `user`를 제외한 오래된 완결
  user/assistant 쌍부터 제거해 요청 메시지를 최대 63개로 만든다. 응답 한 건을 추가한
  뒤에도 최대 64개가 되도록 응답 자리를 하나 남기는 기준이다.
- 대화 맨 앞의 첫 인사는 가장 오래된 메시지가 되면 쌍보다 먼저 단독 제거할 수 있다.
- 256 KiB 요청 상한을 넘으면 같은 방식으로 오래된 완결 대화를 더 제거한다.
- 제거 사실은 대화 맨 위의 `이전 대화 일부는 길이 제한으로 정리됐어요.` 안내로
  표시하되 이 안내는 AI 서버에 보내지 않는다.
- 최신 사용자 메시지와 현재 할 일 목록만으로도 상한을 넘으면 전송하지 않고 입력을
  줄이라는 오류를 보여준다.

### 7.3 데이터 삭제 안내

- 데모 안에는 초기화 버튼을 두지 않는다.
- 개인정보 처리방침에는 브라우저 설정에서 이 사이트의 데이터를 삭제해야 대화와 할
  일이 지워진다고 정확히 안내한다.
- PostHog 실행 코드를 제거한 뒤 과거 로컬 키를 찾거나 지우기 위한 영구 마이그레이션
  코드는 추가하지 않는다. 이미 전송된 원격 데이터 삭제는 이 저장소 범위 밖이다.

## 8. 브라우저와 프록시 계약

### 8.1 `POST /api/chat`

브라우저 요청은 3.3의 `ChatRequest`이며 그 두 필드만 허용한다.

```json
{
  "messages": [{ "role": "user", "content": "요즘 논문 때문에 정신이 없어" }],
  "tasks": []
}
```

- `provider`와 알 수 없는 필드는 거절한다.
- 메시지, 할 일과 UUID는 3.1~3.3의 규칙으로 검증한다.
- 실제 요청 바이트가 256 KiB를 넘으면 AI 서버를 호출하지 않고 413을 반환한다.
- 프록시는 검증된 요청에 `provider`를 추가하지 않고 AI 서버로 전달한다.
- 성공 응답은 3.4의 `ChatResponse | TasksResponse`다.
- AI 서버가 반환한 성공 본문도 브라우저 상태에 반영하기 전에 3.1, 3.2와 3.4로
  검증한다.

### 8.2 AI 서버 주소와 호출

- `UNTANGLE_AI_BASE_URL`은 서버 전용 환경 변수다.
- 값이 없으면 로컬 개발 기본값 `http://127.0.0.1:8000`을 사용한다.
- 시작과 끝의 공백 및 마지막 `/`를 정규화하고 `http:`와 `https:`만 허용한다.
- 경로는 정규화된 주소에 `/v1/chat`을 붙여 만든다.
- 요청은 `Content-Type: application/json`과 `Accept: application/json`을 사용하고 캐시하지
  않는다.
- 프록시 제한 시간은 AI 서버의 기본 총 제한 60초보다 긴 65초다.
- AI 서버의 `X-Request-ID`가 있으면 성공과 오류 응답에 전달한다.

### 8.3 오류 계약

브라우저에 반환하는 오류는 3.5의 `ErrorResponse`와 상태·코드 표를 따른다.

- 실제 본문이 256 KiB를 넘으면 JSON 파싱 전에 `request_too_large`를 반환한다.
- JSON 파싱 실패와 마지막 메시지 역할 오류는 `invalid_request`, 그 밖의 필드·타입·길이·
  개수·UUID·중복 오류는 `validation_error`다.
- 클라이언트는 오류 코드와 관계없이 `error.message`를 표시하고 동일 요청 재시도를
  제공한다.

## 9. 개인정보와 분석 제거

- `posthog-js`, Provider, 페이지뷰·세션 재생·섹션 관찰과 추적 링크를 제거한다.
- `track` 호출과 `data-track-section` 같은 추적 전용 속성을 제거한다.
- `NEXT_PUBLIC_POSTHOG_KEY`, `NEXT_PUBLIC_POSTHOG_HOST`, `POSTHOG_SETUP.md`를 제거한다.
- PostHog 제거를 위해 랜딩 홈 컴포넌트에서 import와 wrapper는 바꿀 수 있지만, 사용자에게
  보이는 본문과 섹션 순서는 바꾸지 않는다.
- 개인정보 처리방침에서 익명 행동 기록, 화면 재생과 PostHog 국외 이전 설명을 제거한다.
- 개인정보 처리방침은 다음 사실을 명시한다.
  - 대화와 할 일은 응답 생성을 위해 랜딩 서버와 선택된 AI 공급자에게 전송된다.
  - 랜딩과 AI 서버는 원문을 영구 저장하거나 애플리케이션 로그에 남기지 않는다.
  - 대화, 할 일과 완료 상태는 사용자의 브라우저에 저장된다.
  - 데모 안의 삭제 버튼은 없으며 브라우저 사이트 데이터 삭제로 제거한다.
- 처리방침의 시행일은 이 변경일로 갱신한다.

## 11. 접근성과 반응형 기준

- 모든 아이콘 버튼은 한국어 접근성 이름을 가진다.
- 탭은 올바른 선택 상태를 노출하고 키보드로 이동할 수 있다.
- 완료 컨트롤은 체크 상태를 보조 기술에 전달한다.
- 편집 UI는 포커스를 가두고 닫을 때 시작 버튼으로 포커스를 돌려준다.
- 삭제 확인은 취소를 기본 안전 동작으로 둔다.
- 드래그만이 유일한 재정렬 수단이 아니어야 한다.
- 입력 글자 크기는 모바일 브라우저 자동 확대를 피하도록 16px 이상으로 유지한다.
- 320px 너비부터 기존 480px 최대 열까지 가로 스크롤이 없어야 한다.
- 가상 키보드가 열려도 입력과 하단 탭의 핵심 조작이 가려지지 않아야 한다.
- 동작 감소 설정에서는 불필요한 이동 애니메이션을 제거한다.

## 12. 검증과 합격 기준

### 12.1 결정론적 상태 테스트

- 저장 데이터 검증, 새 상태와 자동 복원
- 기존 v1 데이터 무시와 손상된 v2 데이터 안전 처리
- user/assistant 추가, 재시도 시 사용자 메시지 비중복
- 64개와 256 KiB 상한의 오래된 대화 정리
- `chat`에서 목록 불변, `tasks`에서 전체 목록 교체
- ID별 완료 보존, 삭제된 ID 정리와 신규 ID 미완료
- 부모·서브태스크 완료 연동
- 직접 추가·수정·삭제·재정렬과 7개 상한

### 12.2 프록시 테스트

- 유효 요청 전달과 `provider` 미전달
- 알 수 없는 필드, 길이, UUID, 중복 ID와 실제 본문 크기 거절
- 성공 `chat`, `tasks` 응답 검증
- AI 서버 오류와 request ID 전달
- 연결 실패, timeout, 잘못된 JSON과 계약 위반 응답의 안전한 매핑
- 로그와 오류에 대화, 할 일, upstream 오류 원문이 포함되지 않음

### 12.3 화면 검증

- 첫 인사, 메시지 전송, 대기, 오류와 재시도
- `tasks` 요약과 수동 `오늘` 이동, 읽지 않음 표시
- 빈 목록, 직접 편집, 완료 그룹과 부모·자식 체크
- 재방문과 날짜 변경 뒤 상태 복원
- 소감 링크와 랜딩 닫기 동선
- 키보드, 접근성 이름, 포커스와 대체 재정렬 수단
- 320px, 390px, 480px 및 넓은 화면의 모바일 열

### 12.4 저장소 검사

- `bun run format`, `bun run lint`, `bun run typecheck`, `bun run test`,
  `bun run build`가 통과한다.
- 실제 로컬 `untangle-ai`와 첫 대화, `tasks` 생성 및 선택 항목 분해를 확인한다.
- `posthog`, 이전 API 경로, 직접 공급자 SDK와 제거된 단계 이름 참조가 남지 않는다.
- 랜딩 홈의 사용자 표시 문구 diff가 없다.

## 13. 주요 위험과 대응

| -------------------------------------------------- | ------------------------------------------------------------ |
| 느린 AI 응답 중 사용자가 목록을 바꿔 결과가 덮임   | 내용 편집을 요청 중 잠그고 완료 상태만 ID로 별도 조정        |
| 장기 대화가 AI 서버 제한을 넘음                    | 오래된 완결 턴을 표시 기록과 요청에서 함께 정리하고 안내     |

| 직접 만든 ID가 AI 응답에서 바뀜                    | UUIDv4를 생성해 현재 목록으로 전달하고 ID 보존 계약을 테스트 |
| 모바일 드래그가 키보드·보조 기술에서 작동하지 않음 | 더보기 메뉴에 위·아래 이동을 동등 기능으로 제공              |
| 프록시가 원문이나 내부 오류를 노출함               | 고정 오류 매핑과 비로깅 테스트로 경계 보호                   |
| PostHog 제거 뒤 문서나 SDK가 남음                  | 의존성·환경 변수·문서와 전체 참조 검색을 완료 게이트로 사용  |

## 14. 설계 결정 요약

- `/demo` 안에서 연속 채팅과 별도 `오늘` 탭을 전환한다.
- Next.js 서버 프록시만 AI 서버와 통신하고 기본 공급자를 사용한다.
- AI 할 일과 로컬 완료 상태를 분리하며 ID로 조정한다.
- 직접 편집한 항목은 브라우저가 UUIDv4를 만들고 다음 AI 요청에 전달한다.
- 새 v2 저장 상태만 자동 복원하고 오래된 대화는 서버 상한 안에서 순차 정리한다.
- 직접 내용 편집은 AI 요청 중 잠그고 완료 체크는 허용한다.
- PostHog과 기존 직접 LLM 호출 경로는 유지하지 않는다.
- 배포 없이 자동 검사, 로컬 연동과 화면 검증에서 종료한다.
